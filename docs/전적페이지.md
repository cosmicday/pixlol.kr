## 경기 링크 — `/summoner/<라이엇 ID>/<경기 번호>` (2026-08-14 신설)

친구에게 특정 경기를 통째로 보낼 수 있는 주소. 경기 칸 오른쪽 위 🔗 를 누르면 복사된다.

- **★ 서버는 손댈 게 없다.** `server.js` 맨 끝 `app.get(/.*/, sendIndexHtml)` 가 모든 주소에
  index.html 을 주고, 라우팅은 `app.js` 진입부가 `location.pathname` 을 잘라서 한다.
  **새 주소를 만들 땐 `app.js` 의 `pathParts` 분기와 `popstate` 두 곳을 같이 고칠 것** —
  한쪽만 고치면 뒤로가기로 들어왔을 때 다르게 동작한다 (랭킹 헤더에서 겪은 것과 같다)
- **★ `executeSearch` 의 `pushState` 가 경기 번호를 지워 버린다.** 검색이 끝나면
  `/summoner/<이름>` 을 밀어 넣는데, 링크로 들어온 경우 **펼치기도 전에** 주소가 바뀌어
  새로고침하면 링크가 죽는다. `window.pendingMatchId` 가 있으면 주소에 같이 붙인다
- **검색은 최근 20판만 받아온다.** 그보다 오래된 경기는 `openPendingMatch()` 가
  "더 보기"를 **최대 3번**(총 50판) 눌러 가며 찾고, 못 찾으면 안내를 띄운다.
  더 늘리면 라이엇 호출만 늘어난다
- **★ 복사 버튼은 `.toggle-btn` 위에 겹쳐 있다.** 토글은 오른쪽 35px 을 **세로로 다 쓰는데**
  화살표는 맨 아래에만 있어서(`align-items: flex-end`) 위쪽이 비어 있다. 그 자리를 쓴다.
  그래서 두 가지가 필수다 — **`z-index: 2`**(없으면 클릭이 토글에 먹힌다)와
  **`stopPropagation`**(없으면 주소만 복사하려다 상세가 같이 열린다). 둘 다 실측 확인했다
- **주소에 넣는 이름은 라이엇이 준 정본(`currentProfileName`, `이름#태그`)이다.**
  검색창에 친 글자를 쓰면 대소문자가 제각각인 주소가 돌아다닌다
- **★★ `navigator.clipboard` 는 문서에 포커스가 없으면 실패한다 — 헤드리스에서는 항상 실패다.**
  `Emulation.setFocusEmulationEnabled` 를 안 켜고 재고는 **"복사 기능이 고장났다" 고 오진했다.**
  켜니까 바로 성공했다. `execCommand` 폴백도 포커스가 필요해서 같이 실패하니
  **폴백까지 실패한다고 코드 탓으로 몰지 말 것**
- 링크 미리보기 카드(`og:title`)는 아직 없다. 하려면 `sendIndexHtml` 이 그 주소일 때만
  DB 를 한 번 더 읽어 메타 태그를 끼워야 한다

## 상세 전적 표 폭 (2026-08-18 정비)

**표가 상세 상자보다 6px 넓어서 간단 전적 카드·탭 줄과 오른쪽 끝이 안 맞았다.**
`<colgroup>` 의 열 폭이 **열 칸 모두 고정 px** 이고 그 합이 735px 인데 상자는 729px 이었다.
`table-layout: fixed` 라 지정 합계가 그대로 표 폭이 되어 그만큼 삐져나온다.

- **★ 첫 칸(소환사)만 폭을 안 정한다.** 나머지 아홉 칸 합 585px 은 그대로 두고 남거나
  모자란 폭을 첫 칸이 흡수한다. **협곡·칼바람 표와 아레나 표 둘 다 같은 구조다**
  (`app.js` 에 `<colgroup>` 이 두 군데 있다 — 같이 고칠 것)
- **★★ `min-width` 를 예전 폭 합(735px)으로 두면 안 된다.** 상자가 729px 라
  **min-width 가 `width: 100%` 를 이겨서 늘 6px 넘치는 예전 상태 그대로가 된다.**
  실제로 한 번 그렇게 났다. `585 + 첫 칸 하한 120 = 705px` 로 잡는다
- **★ 폰 블록에 있던 `min-width: 650px` 은 지웠다.** 두 곳에 두면 어긋나고,
  애초에 고정 합이 735 라 그 값은 한 번도 작동한 적이 없었다
- 실측: 창 1400/1200 에서 카드·탭줄·상자·표가 모두 729px 이고 오른쪽 끝이 같다.
  좁은 창(1000/900)은 표가 705px 로 예전 735px 보다 30px 덜 넘친다.
  폰 390px 은 예전처럼 가로 스크롤로 처리되고 넘침 0
- **★ 아레나 표는 화면 확인을 못 했다** — `matchcaches` TTL 이 3일이라 지금 캐시에
  아레나 경기가 없다. 구조가 같아 동작은 같을 텐데 한 번 볼 것

## 전적 요약 통계 박스 (2026-08-14 정비)

`renderSummaryStats` 가 모드별로 패널 셋 중 하나를 그린다 —
협곡(`renderSummaryStats` 본체) / 칼바람(`renderAramSummaryHtml`) / 아레나(`renderArenaSummaryHtml`).
**셋이 같은 골격을 복붙해 쓰므로 한쪽만 고치면 필터를 누를 때 박스가 흔들린다.**

- **★ 오른쪽 칸 폭은 세 패널 모두 176px 이어야 한다.** 칼바람만 181px 이던 때
  구분선이 협곡·아레나보다 **1px·4px 왼쪽**에 찍혔다 (가로 238/508 → 237/504, 실측).
  박스가 `justify-content: space-between` 이라 **칸이 5px 넓어지면 남는 폭을 다시 나눠서
  구분선 네 자리가 전부 밀린다.** 구분선 자체(1x90)는 셋이 원래 같았다 —
  "구분선이 다르다" 는 증상의 원인이 구분선이 아니었다
- **★ 가운데 칸 폭은 258px 이다** (2026-08-14에 244 → 258). 승패가 두 자리(`15승 / 15패`)면
  안쪽 span 62px 을 넘겨 **줄이 넘어갔다.** span 을 76px(숫자 두 자리분)로 넓히고 칸도
  좌우로 한 자리씩 늘렸다. 실측으로 `15승 / 15패` 까지 한 줄이고,
  `100승 / 100패`(세 자리)는 8px 넘치지만 `white-space: nowrap` 이라 줄은 안 넘어간다
- **★ 가운데 칸의 줄 높이(28px + margin 6)를 바꾸면 안 된다.** 가운데 칸(129px)이
  박스 높이(181px)를 정하는 칸이라, 줄 높이가 달라지면 **모드마다 박스 높이가 달라져
  필터를 누를 때 아래 목록이 위아래로 튄다.** 항목이 3개가 안 되면 빈 줄로 채우는 이유다
- **칼바람·아레나는 "플레이한 챔피언" 대신 "플레이한 역할군" 이다** (`renderRoleRowsHtml`).
  두 모드는 라인이 없어 챔피언을 나열해도 성향이 안 보인다
  - **★ 역할군은 `fetchChampionMap()` 이 채운다 — 추가 요청이 0이다.** 전적 페이지가
    이미 `champion.json` 을 받고 있었다(`championIdMap`·`korChampMap` 용). 거기서 `tags` 를
    같이 담는다. **`showChampions()` 와 같은 표(`champRoleMap`)를 쓰고 `isClassicChamp`
    가드도 똑같이 걸어야 한다** — 클래식 챔피언이 섞이면 스탯 탭 역할군 평균의 모집단이 흔들린다
  - **챔피언 하나가 역할군 2개에 들어가므로 역할군별 게임 수의 합 > 총 게임 수다.** 정상이다
  - **★ 아레나만 문법이 다르다 — `N게임 우승 N회`.** 아레나는 승패가 아니라 등수이고
    (경기 칸도 `placementText` 로 등수를 찍는다), 같은 패널 왼쪽에 "평균 등수" 가 있는데
    옆에서 승률을 말하면 서로 어긋난다. 칼바람은 `(N승 N패 N%)` 다

## 아레나 밴 (2026-08-14 조사)

**★★ 아레나는 밴이 있다. 코드 주석이 "칼바람·아레나는 밴이 없다" 고 적고 있었는데 틀렸다.**
MongoDB `matchcaches` 의 아레나 153판 전수로 확인했다.

| | 값 |
|---|---|
| 참가자 수 | 18명 149판(6조 x 3명) / 16명 4판(구버전 8조 x 2명) |
| 밴 개수 | **참가자 수와 정확히 일치 — 1인 1밴** |
| 실린 곳 | 153판 전부 `teams[0]`(teamId 100) 한 곳. `teams[1]` 은 **`teamId: 0`** 에 빈 배열 |
| `pickTurn` | 153판 전부 1..N 연속 |
| `-1`(시간 초과) | 2746개 중 497개(18%) |

- **★ 그래서 `renderTeamSummaryRow` 가 아레나 밴을 통째로 버리고 있었다.** 이 함수는
  `teamId === 200` 을 찾아 없으면 `return ''` 하는데 아레나엔 **100 과 0** 뿐이다.
  게다가 아레나 상세는 `renderArenaDetail()` 이라는 별도 경로라 그 함수를 부르지도 않는다.
  지금은 아레나 상세 표 맨 아래에 `.arena-ban-summary` 줄로 18개를 한 줄에 깐다
- **★ 아레나의 `teamId` 는 진영이 아니라 "상위 절반 / 하위 절반" 이다** (153/153 확인).
  1~3등 조가 100, 4~6등 조가 200 이다. 그래서 **밴 출처를 가르는 데 못 쓴다**

**★★ 밴이 누구 것인지 라이엇은 안 알려준다. 그런데 순서에 답이 있다 (통계로 확인).**
`bans` 항목엔 `championId` 와 `pickTurn` 뿐이고 puuid 도 조 번호도 없다.

- **① `pickTurn` 은 "밴 넣은 순서" 가 아니라 고정 자리다.** `-1`(시간 초과) 비율을
  자리별로 세니 1~18번이 **13~26% 로 고르다.** 넣은 순서 기록이었으면 시간 초과가
  뒷번호에 몰려야 한다
- **② 그 자리는 조 번호 순으로 3개씩 묶여 있다** — `pickTurn 1~3 = 조1, 4~6 = 조2, …
  16~18 = 조6`. 검증법: **사람은 밴 습관이 있다.** 같은 puuid 가 여러 판에 나올 때
  가설대로 배정한 밴이 판마다 반복되는지를 센다. **두 판에 겹치는 사람이 본인뿐인
  매치쌍만** 남겨 같은 파티가 연달아 한 경우를 걷어냈다

  | 배정 가설 | 같은 사람의 밴이 반복될 확률 |
  |---|---|
  | 무작위 (대조군) | 1.5 ~ 2.4% |
  | 참가자 배열 순서 그대로 | 2.9% — **대조군과 구분 안 됨, 틀렸다** |
  | **조 번호 순** | **9.2%** (z ≈ 10) |

  조 단위(3개 묶음) 겹침은 **40.5% vs 무작위 14.1%**. 조↔블록 대응을 한 칸씩 밀어 보면
  `r=0` 40.5% / 나머지 다섯은 12.6~19.7% 라 **어긋난 배치는 전부 떨어진다**
- **블록 안 3자리 중 누구인지는 약하다** — 참가자 배열 등장 순 9.2% / 뒤집기 6.6% /
  한 칸 회전 4.1%. **조 단위는 확실하고 개인 단위는 유력** 정도다
- **★ 아직 인게임 확인을 안 했다.** 아레나 한 판에서 내 조 3명의 밴만 적어 두면 끝난다 —
  그 3개가 `pickTurn (조번호-1)*3+1 ~ +3` 에 들어 있는지 보면 된다.
  조가 6개라 우연히 맞을 확률이 낮아 **한 판으로 갈린다**
- 서버는 `bans` 를 **`pickTurn` 순서로 못 박아** 내려보낸다 (`buildHistoryEntry`).
  이 순서가 곧 조 순서라서, 확인이 끝나면 3개씩 잘라 쓰기만 하면 된다

**★ 아레나 밴 관련 사실을 "라이엇 데이터끼리 대조" 로는 못 얻는다.** `teams[0]` 에
전부 몰려 있다는 것도, `teamId 0` 이라는 것도 스키마상 이상하지 않아서 기계 검사에
안 걸린다. **실제 데이터를 세어 봐야 드러난다** — 위 "라이엇 데이터끼리만 대조하면"
항목과 같은 종류의 함정이다.
